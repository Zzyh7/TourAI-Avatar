## 1. 产品概述

### 1.1 产品定位

**景区导览AI数字人**是一款面向景区游客的智能导览产品。通过数字人形象 + 实时语音对话 + 拍照识景 + 个性化推荐，为游客提供沉浸式、智能化的景区游览体验。

### 1.2 核心能力

| 能力模块 | 说明 |
|---------|------|
| 🗣️ **智能问答** | 基于 RAG 知识库 + LLM，回答景区历史、文化、景点特色等各类问题 |
| 🎤 **语音对话** | 前端语音识别 → 后端 TTS 合成，实现自然语言语音交互 |
| 📷 **拍照识景** | 多模态大模型识别景点照片，实时讲解历史背景和建筑特色 |
| 📍 **地图服务** | 集成高德 MCP，支持景点搜索、周边 POI、天气查询、路线规划 |
| 🧭 **个性化推荐** | 根据游客标签（家庭游/情侣游/文化深度游/休闲游）推荐定制路线 |
| 📚 **知识库管理** | 管理后台上传景区文档，自动分块、向量化、混合检索 |
| 💬 **情感感知** | LLM 分析用户消息情感倾向，辅助服务质量监控 |
| 👤 **数字人展示** | 前端 Live2D 数字人形象，配合语音播报的表情和口型变化 |

### 1.3 与旧版 TravelAgent 的关系

本项目从 [旧版 TravelAgent](../README.md)（CLI + Streamlit 旅行规划助手）演进而来，核心变更：

| 维度 | 旧版 | 新版 |
|------|------|------|
| **产品形态** | 旅行规划工具 | 景区导览数字人 |
| **用户界面** | Streamlit Web / CLI | React 前端 + Live2D 数字人 |
| **LLM** | 通义千问 (qwen3-max) | DeepSeek-Chat |
| **对话模式** | 一问一答文本 | SSE 流式 + 音频实时播报 |
| **知识库** | 无 | FAISS + BM25 混合检索 RAG |
| **语音** | 无 | Edge-TTS 语音合成 |
| **多模态** | 无 | 通义千问-VL 拍照识景 |
| **后端框架** | Streamlit 内嵌 | FastAPI + 异步架构 |
| **数据库** | 无 | SQLite (会话/对话/文档/景点) |
| **管理后台** | 无 | 知识库管理 / 统计 / 配置 |
| **部署** | 单机脚本 | Docker Compose |

## 3. 技术栈选型

### 3.1 完整技术栈

| 层级 | 技术 | 版本 | 选型理由 |
|------|------|------|---------|
| **LLM (主对话)** | DeepSeek-Chat (OpenAI 兼容) | - | 性价比高、中文能力强、API 兼容无需额外适配器 |
| **LLM (多模态)** | 通义千问-VL (qwen-vl-max) | - | 支持图像输入，中文场景理解好 |
| **嵌入模型** | BAAI/bge-small-zh-v1.5 | - | 中文语义检索 SOTA，仅 24MB，可本地 CPU 运行 |
| **Agent 框架** | LangChain + LangGraph | latest | 成熟的 Agent 开发框架，create_agent 一键创建 ReAct Agent |
| **MCP 协议** | langchain-mcp-adapters | latest | LangChain 原生 MCP 集成，SSE 传输连接高德地图 |
| **后端框架** | FastAPI | >=0.110 | 高性能异步框架，原生 SSE 支持，自动生成 OpenAPI 文档 |
| **TTS** | Edge-TTS (微软) | latest | 免费、中文自然度高、离线可运行 |
| **向量数据库** | FAISS (Meta) | latest | 轻量级、单机高性能、支持增量添加和持久化 |
| **关键词检索** | BM25 (rank-bm25) | latest | 经典算法，配合 jieba 中文分词 |
| **分词** | jieba | latest | 中文分词标杆 |
| **数据库 ORM** | SQLAlchemy 2.0 | latest | Python 最成熟的 ORM，支持 SQLite |
| **前端框架** | React 18 + TypeScript | latest | 生态丰富、类型安全 |
| **构建工具** | Vite | latest | 极快的 HMR，开发体验好 |
| **容器化** | Docker + Docker Compose | - | 标准化部署，环境一致 |
| **语音识别** | 浏览器 Web Speech API | - | 前端原生支持，无需额外服务 |

### 3.2 选型考量

**为什么选用 DeepSeek 而非通义千问作为主 LLM？**
- OpenAI 兼容接口，使用 langchain_openai 标准适配器，避免通义千问的 monkey-patch 问题（旧版曾因 `subtract_client_response` 的 KeyError bug 需要手动修复）
- 中文能力出色，价格更低

**为什么有两套 RAG 实现？**
- `backend/services/rag/`：旧版简化 RAG，供 `backend/admin/knowledge.py` 使用
- `backend/rag_system/`：增强版 RAG，支持混合检索 + RRF 融合 + FAQ 独立索引，设计为可独立部署的子系统

**为什么 RAG 的 LLM 调用直接使用 langchain_openai 原始 API？**
- RAG 问答是纯文本生成任务，不需要 Agent/工具调用，直接用 LLM 更高效
- 减少依赖层级，避免 Agent 框架的额外开销

#### 5.2.2 GuideAgent (总控)

**文件**: [backend/agents/planner.py](../backend/agents/planner.py)

`GuideAgent` 是系统的**门面 (Facade)**，对外暴露简洁的 `invoke()` / `stream()` 接口，隐藏内部多 Agent 复杂性。

**build() 五阶段**：

```
Phase 1: 按领域加载 MCP 工具
  poi_tools    ← mcp.get_tools_for("poi")      # maps_text_search, maps_search_detail
  weather_tools ← mcp.get_tools_for("weather")  # maps_weather
  route_tools   ← mcp.get_tools_for("route")    # maps_direction_*_by_address
  around_tools  ← mcp.get_tools_for("around")   # maps_around_search

Phase 2: 创建 3 个 SpecialistAgent
  WeatherAgent    ← llm + WEATHER_AGENT_PROMPT + weather_tools
  AttractionAgent ← llm + ATTRACTION_AGENT_PROMPT + (poi_tools + around_tools)
  RouteAgent      ← llm + ROUTE_AGENT_PROMPT + route_tools

Phase 3: 子 Agent 包装为 @tool 函数
  query_weather(query)     → self._weather_agent.invoke(query)
  search_attraction(query) → self._attraction_agent.invoke(query)
  search_route(query)      → self._route_agent.invoke(query)

Phase 4: RAG 工具
  search_knowledge(query)  → self.rag_retriever.retrieve(query)

Phase 5: 组装 GuideAgent
  create_agent(llm, [query_weather, search_attraction, search_route, search_knowledge],
               GUIDE_AGENT_PROMPT)
```

**stream() 事件处理**：

| 事件类型 | 来源 | 处理 |
|---------|------|------|
| `on_chat_model_stream` | LLM 输出 token | 过滤 TOOL_CALL 泄漏 → yield `{type: "token", data}` |
| `on_tool_start` | 工具开始执行 | 映射到中文标签 (🌤️查询天气 / 🏛️搜索景点 / 🗺️规划路线 / 📚检索知识库) |
| `on_tool_end` | 工具执行完成 | 记录状态（不输出到前端避免刷屏） |

**`[TOOL_CALL:...]` 泄漏过滤**：子 Agent 的 system prompt 要求使用 `[TOOL_CALL:amap_maps_xxx:...]` 格式调用工具。当子 Agent 通过 `ainvoke()` 返回时，内部 ReAct 循环的中间文本可能被追加到结果中。通过正则 `_TOOL_CALL_PATTERN` 在 stream 中过滤。

#### 5.2.3 SpecialistAgent (领域专家)

**文件**: [backend/agents/specialist.py](../backend/agents/specialist.py)

可复用的 Agent 基类：

```python
class SpecialistAgent:
    def __init__(llm, name, system_prompt, tools)
        # 存储配置，_agent 延迟到 build() 创建

    async def build()
        # create_agent(model, tools, system_prompt) → LangGraph Agent

    async def invoke(user_input) → str
        # ainvoke → 返回最后一条消息的 content

    async def stream(user_input) → AsyncIterator[str]
        # astream_events v2 → 逐 token yield
```

**最小权限原则**：每个 SpecialistAgent 只持有自己领域的工具。WeatherAgent 只有 `maps_weather`，AttractionAgent 只有 POI 搜索+周边搜索，RouteAgent 只有路线规划。这防止了 Agent 误用不属于自己领域的工具。

#### 5.4.2 核心组件详解

**文档加载器** ([loader.py](../backend/rag_system/loader.py)):
- PDF → PyPDFLoader (逐页提取)
- Word → Docx2txtLoader
- TXT → TextLoader (UTF-8)
- Markdown → UnstructuredMarkdownLoader (不可用时回退 TextLoader)
- 自动注入 `metadata["source"]` 文件名

**文本分块器** ([splitter.py](../backend/rag_system/splitter.py)):
- `RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)`
- 分隔符优先级：段落 `\n\n` → 换行 `\n` → 句号 `。` → 感叹号 `！` → 问号 `？` → 分号 `；` → 逗号 `，` → 空格 → 字符
- 保证句子完整性，不会截断到词语中间

**向量化服务** ([embedding.py](../backend/rag_system/embedding.py)):
- 模型：`BAAI/bge-small-zh-v1.5` (24MB, 512维归一化向量)
- `normalize_embeddings=True` → 向量 L2 归一化
- FAISS `IndexFlatIP` (内积) = 余弦相似度

**混合检索器** ([hybrid_retriever.py](../backend/rag_system/hybrid_retriever.py)):
- 维护三个独立索引：FAISS 文档 + BM25 关键词 + FAQ 精确匹配
- 所有索引支持持久化到磁盘、增量添加、启动时自动恢复

#### 5.4.3 RRF 融合算法

核心公式：`RRF_score(d) = Σ_i 1/(k + rank_i(d))`

- k = 60（平滑排名差异）
- rank_i(d) = 文档 d 在第 i 个检索器中的排名（1-indexed）

示例：
```
文档A: FAISS#1, BM25#5
  RRF = 1/(60+1) + 1/(60+5) = 0.01639 + 0.01538 = 0.03178

文档B: FAISS#3, BM25#2
  RRF = 1/(60+3) + 1/(60+2) = 0.01587 + 0.01613 = 0.03200

→ 文档B 胜出！（两个检索器都表现不错 > 单个检索器排名最高）
```

**去重策略**：使用文档内容前 80 字符作为近似标识。同一文档在 FAISS 和 BM25 中都出现时，RRF 分数累加。

#### 5.4.4 FAQ 独立索引

- 独立的 FAISS 索引 + JSON 答案映射
- 更高的匹配阈值 (0.85 vs 0.35)
- 检索优先级最高：FAQ 命中 → 直接返回预写答案，跳过混合检索和 LLM 生成

#### 5.4.5 兜底策略

FAISS 最高余弦相似度 < `score_threshold` (0.35) → 触发"资料不足"响应：
```
"抱歉，关于这个问题我暂时还不太了解。资料库中暂无相关信息，
 建议您咨询景区工作人员或查阅官方资料。"
```
这避免了 LLM 在缺乏依据时强行编造答案（幻觉）。

#### 5.4.6 文档存储

**文件**: [document_store.py](../backend/rag_system/document_store.py)

```
  └── 1:N → chunks 表
```

```
      ├── tool_start → SSE event: tool {status, label}
      │
      └── done → 保存对话记录 + 情感分析 → SSE event: done
```

### 7.2 拍照识景数据流

```
用户拍照/选图
      │
      ▼
PhotoRecognition 组件
      │
      ├── Canvas 压缩 (max 1024px, JPEG 0.8)
      ├── FileReader → base64
      │
      ▼
POST /api/photo-recognize {image: base64}
      │
      ▼
通义千问-VL (qwen-vl-max)
  HumanMessage([
    {type: "text", text: PHOTO_RECOGNITION_PROMPT},
    {type: "image_url", image_url: {url: "data:image/jpeg;base64,..."}}
  ])
      │
      ▼
返回 → {description: "口语化讲解文本"}
      │
      ▼
前端追加到 messages 列表展示
```

### 7.3 GPS 附近景点数据流

```
前端获取 GPS 坐标 (navigator.geolocation)
      │
      ▼
GET /api/nearby-spots?lat=30.25&lng=120.13&radius=500
      │
      ▼
数据库查询 scenic_spots 表 → Haversine 距离计算 → 半径过滤
      │
      ▼
返回 → {spots: [{name, distance_m, description, category, ...}]}
```

## 11. 设计模式总结

| 模式 | 应用位置 | 说明 |
|------|---------|------|
| **单例模式** | `McpClientManager` / `Config` / `EdgeTTSService` | 全局唯一实例，避免重复连接和初始化 |
| **门面模式** | `GuideAgent` | 对外暴露简洁 `invoke()`/`stream()`，隐藏 4 个子 Agent + MCP 复杂性 |
| **装饰器模式** | `@tool` 包装子 Agent | 将 SpecialistAgent 适配为 LangChain Tool 接口 |
| **策略模式** | `tool_domains` 字典 / `routes_pool` | 工具按领域分组，运行时按需选择 |
| **模板方法** | `SpecialistAgent.build()` | 子类可覆盖构建逻辑 |
| **适配器模式** | `search_knowledge` Tool | 将 RAG 检索器适配为 Agent 可调用的 Tool 接口 |
| **观察者模式** | SSE 流式事件 | `astream_events` v2 发布事件，前端订阅消费 |
| **命令模式** | 子 Agent 的 TOOL_CALL 格式 | 约束式 Prompt 实现结构化命令调用 |
| **工厂方法** | `Config.create_llm()` / `Config.create_multimodal_llm()` | 统一 LLM 实例创建 |
| **门面 + 子系统** | `rag_system/__init__.py` | 对外暴露 6 个公共 API，隐藏内部 7 个模块 |
| **懒加载** | RAG 服务的 `get_xxx()` 函数 | 首次访问时才初始化模型和索引 |
| **双检索 + RRF 融合** | `HybridRetriever` | 语义 + 关键词双路检索，排名空间融合消除量纲差异 |

## 12. 安全性设计

| 方面 | 措施 |
|------|------|
| **API Key 保护** | 通过 `.env` 文件加载，不硬编码；Docker 通过 volume 挂载 |
| **CORS** | 开发阶段 `allow_origins=["*"]`，生产应限制为实际域名 |
| **SQL 注入** | SQLAlchemy ORM 参数化查询，无原始 SQL 拼接 |
| **文件上传** | 校验文件扩展名白名单；限制文件类型 |
| **反 hallucination** | RAG 阈值兜底 (低于 0.35 直接说"不知道")；Prompt 严禁编造 |
| **速率限制** | 当前未实现，建议后续接入 (nginx rate limiting 或 FastAPI middleware) |
| **输入校验** | Pydantic BaseModel 自动校验请求体 |

## 13. 性能优化策略

| 策略 | 应用位置 | 说明 |
|------|---------|------|
| **懒加载 + 缓存** | MCP 工具列表 | 首次请求后缓存，避免每次对话都重新获取 15 个工具 |
| **单次初始化** | GuideAgent.build() | `_agent is not None` 守卫，防止重复创建 |
| **流式输出** | 所有 Agent | 逐 token yield，用户可在 1-2 秒内看到首个 token |
| **句级 TTS** | chat() 端点 | 检测句号即合成，而非等完整回答后一次合成 |
| **FAISS 增量添加** | HybridRetriever | `add_documents()` 增量追加向量，不重建整个索引 |
| **BM25 快速重建** | HybridRetriever | BM25 不支持增量但重建速度极快 (O(n)) |
| **argpartition** | BM25 检索 | 使用 `np.argpartition` 部分排序获取 top-k，非完整排序 |
| **WAL 模式** | SQLite | `PRAGMA journal_mode=WAL` 提升并发读写性能 |
| **BGE 本地运行** | EmbeddingService | 24MB 模型 CPU 运行，无网络延迟 |
| **独立 RAG 子系统** | rag_system/ | 可独立部署到单独容器，横向扩展 |
